# ToastMonitor on Windows

The Windows app is an additive front end to the existing repository, not a separate core extraction. `Windows/` contains the SwiftCrossUI 0.10.0 WinUI front end and the small native Win32 Explorer taskbar host. The shared `ToastMonitor` module is compiled from the existing `Sources/ToastMonitor` files in place through the conditional root package manifest; the original macOS SwiftUI target and test graph remain intact. Keep platform-specific code in the existing Windows front end and narrow OS adapters rather than moving parsers, accounting, or database code into a new target.

## Build and package

Use 64-bit Windows with Visual Studio 2022 C++ x64 build tools and a Windows SDK. Install the official [Swift 6.1.3 Windows x64 toolchain](https://download.swift.org/swift-6.1.3-release/windows10/swift-6.1.3-RELEASE/swift-6.1.3-RELEASE-windows10.exe); the script locates the matching SDK and runtime beside the selected compiler.

The build script prepares the official SQLite 3.54.1 x64 DLL and matching header from SHA-256-pinned SQLite downloads, then generates `sqlite3.lib` with Visual Studio's `lib.exe`. This avoids Windows SDK `winsqlite3`'s omitted `localtime` support and leaves shared SQLite queries, including timezone/DST behavior, unchanged.

Swift 6.1.3 Foundation on Windows can treat the localized standard-time display name as a Windows timezone ID and fall back to GMT when ICU cannot map it. Before database or CLI startup, the Windows adapter maps the stable Windows timezone key to an IANA identifier through the SDK ICU, then temporarily exposes that ID in the process OS environment while resetting and priming Foundation's timezone/calendar caches. It restores the prior environment before work begins; it does not change the CRT environment or leak the temporary value to child processes. Explicit `TZ`/`TZFILE` overrides are preserved, and the IANA mapping supplies real historical and DST rules rather than a fixed offset. The adapter runs at startup only; restart ToastMonitor after changing the Windows timezone to resynchronize. Live timezone changes are not monitored or verified. Re-evaluate this compatibility adapter when updating Swift.

For pinned `swift-winui` 0.2.2, the script applies the STA threading correction required by the Windows App SDK contract. For pinned `swift-cross-ui` 0.10.0, it applies the WinUI patch in `Windows/Patches/swift-cross-ui-0.10.0-winui.patch`: the STA-safe redirected-activation correction lets the receiving instance handle activation without blocking its UI thread, and the receiver owns presentation rather than forcing the primary window forward. For DPI-aware text sizing, each `CustomWindow` stores one optional measurement `TextBlock` bound once to that window's `XamlRoot`; widgets without a matching window root continue to use the original detached helper. The patch avoids clearing or reassigning `XamlRoot` and reuses the window-bound helper rather than allocating one per measurement; fractional desired width and height are rounded up to integer layout allocations. Each patch is pinned to its package revision and exact normalized source preimage/postimage hashes, failing closed on changed upstream code. Re-evaluate both patches when updating either dependency; these build-time corrections alone are not GUI or accessibility acceptance proof.

### Native launcher and application DLL

`ToastMonitor.exe` is a small native C launcher. It calls the exported `ToastMonitor_main(argc, argv)` entry point in the adjacent `ToastMonitorRuntime.dll`. The DLL owns the existing Swift application and its package implementations; the `ToastMonitor` module name, shared source paths, test imports and macOS build remain unchanged.

This is **application-level dynamic linkage**, not independently installable SwiftCrossUI, WinUI or Crypto DLLs. A direct dynamic-product build of the pinned WinUI projection graph exceeded Windows' PE export-table limit. Keeping its original static products inside the application DLL avoids splitting generated bindings or maintaining new dependency-manifest patches. Moving the code out of the EXE does not reduce the total application code size.

The official script builds the Swift DLL, then compiles `Windows/Launcher/main.c` with the Visual C++ dynamic CRT. It packages that exact DLL rather than globbing stale libraries from the build cache. The existing STA and SwiftCrossUI backend patches remain required; no additional dependency-source patch or app/core extraction is introduced.

### End-user runtime prerequisites

The ZIP contains `ToastMonitor.exe`, `ToastMonitorRuntime.dll`, the application-local WinAppSDK bootstrap resource, build metadata and license/notice texts. It does **not** contain the Swift/Visual C++/SQLite runtime DLLs, a runtime installer or a DDLM MSIX. Users must provision these system runtimes before launching it:

- **Swift 6.1.3 x64 runtime**, including Foundation/ICU, Dispatch and WinSDK. The [official Swift installation](https://download.swift.org/swift-6.1.3-release/windows10/swift-6.1.3-RELEASE/swift-6.1.3-RELEASE-windows10.exe) supplies them. Its `Runtimes/6.1.3/usr/bin` directory must be on the launching process's PATH.
- **Microsoft Visual C++ x64 runtime** compatible with Visual Studio 2022; see Microsoft's [redistributable guidance](https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files?view=msvc-170).
- **SQLite 3.54.1 x64**, with the official `sqlite3.dll` directory on PATH. Windows' `winsqlite3.dll` is not a substitute for this port's local-time queries.
- **Windows App Runtime 1.5 x64**, installed and registered for the current user. Obtain Microsoft's [runtime installer separately](https://aka.ms/windowsappsdk/1.5/1.5.250108004/windowsappruntimeinstall-x64.exe); it is not in the ZIP.

The matching WinAppSDK 1.5 bootstrap DLL **is shipped** in `swift-winui_CWinAppSDK.resources/Microsoft.WindowsAppRuntime.Bootstrap.dll`. The pinned [Microsoft.WindowsAppSDK 1.5.240607001 NuGet](https://api.nuget.org/v3-flatcontainer/microsoft.windowsappsdk/1.5.240607001/microsoft.windowsappsdk.1.5.240607001.nupkg) supplies it; its verified SHA-256 is `9d2533fb9aa085bc4bc9ac2b3d5b5daec3f44ed7feb08ba8161dc851311368f8`.

Keep the application DLL and resource directory beside the launcher. Launch from the extracted application directory, as the pinned WinUI loader uses a relative `LoadLibrary` path for the bootstrap. No dependency-loader patch or new bootstrap discovery mechanism is introduced.

`ThirdPartyNotices/` retains the pinned runtime and resolved SwiftPM license/notice texts; these texts do not imply that runtime binaries are redistributed. The CLI requires the external Swift/Visual C++/SQLite runtimes, but its cached-usage/diagnostics paths do not initialize WinUI.

From PowerShell at the repository root:

```powershell
.\Windows\Scripts\build.ps1 -Action resolve
.\Windows\Scripts\build.ps1 -Action build
.\Windows\Scripts\build.ps1 -Action test
.\Windows\Scripts\build.ps1 -Action run
.\Windows\Scripts\build.ps1 -Action package -Configuration release
```

`resolve` prepares package checkouts, the pinned SQLite runtime/import library, and the guarded WinUI patches without compiling.

If the WinUI bootstrap reports `0x80670016` on Windows 10 even though Windows App Runtime 1.5 frameworks are installed, the observed cause was missing per-user registration of the matching DDLM. The official runtime installer's `--quiet --repair` returned 0 but did not repair that registration. For this specific failure, obtain the signed DDLM MSIX separately from `tools/MSIX/win10-x64/Microsoft.WindowsAppRuntime.DDLM.1.5.msix` in the pinned NuGet, then validate and register it for the current user:

```powershell
$ddlm = '<extracted-NuGet-directory>\tools\MSIX\win10-x64\Microsoft.WindowsAppRuntime.DDLM.1.5.msix'
signtool.exe verify /pa /v $ddlm
Add-AppxPackage -Path $ddlm -ErrorAction Stop
```

This is a manual repair, not an automatic app action; an installer exit code of 0 alone does not establish that GUI startup works.

The script defaults to two Swift build jobs to limit peak memory; set `-Jobs` to change it. `run` forwards remaining arguments to the executable. To choose the compiler and keep scratch files off the system drive, use `.\Windows\Scripts\build.ps1 -Action build -SwiftPath 'C:\Swift\Toolchains\6.1.3+Asserts\usr\bin\swift.exe' -BuildPath 'G:\ToastMonitorBuild'`. The package action writes the DLL-based `dist/ToastMonitor-Windows-x64.zip` and refuses to overwrite an existing package directory. CI requires the application DLL and bootstrap resource, rejects bundled system runtimes/installers, and exercises the extracted CLI with external Swift/SQLite runtime directories on PATH; its artifact is available from [the Windows workflow](https://github.com/yeyebbc/ToastMonitor/actions/workflows/windows.yml).

For isolated CLI checks, set `TM_DATABASE_PATH` to a temporary database location before running the packaged executable. `--print-usage` emits JSON; `--export-diagnostics <path>` exports diagnostics and `--help` lists command options. The default database is `%LOCALAPPDATA%\ToastMonitor\toastmonitor.db`. Do not use a real profile when smoke-testing commands that can write data.

## Launch and collection lifecycle

From the extracted package directory, start collection without showing a window:

```powershell
./ToastMonitor.exe --background
```

Neither background startup nor a background secondary launch shows or activates a window. A normal launch, `--show-dashboard`, or `--show-settings` explicitly presents the requested window. With taskbar integration available, closing a window or pressing Escape hides it while collection continues. The existing host-unavailable exception keeps Usage available as an ordinary app window: closing Usage exits the app, and Escape does not hide it. Dashboard and Settings still hide on close. Quit exits the app, removes any taskbar readout, and restores the taskbar reservation owned by the app.

## Windows behavior and limits

- Today's usage is embedded in the primary horizontal Explorer taskbar, not the notification tray. Left-click opens the app. If integration is unavailable, the ordinary app window remains available and reports the error; Explorer recovery is retried. Vertical/secondary taskbars and tray fallback are unsupported. Win11 placement uses a conservative UIAutomation gap and has not been verified.
- A hard crash or forced termination cannot run in-process taskbar cleanup, so Explorer may retain the reservation gap until it relayouts. Normal Quit cleanup is implemented and was verified to remove the readout and restore the app-owned reservation.
- The native taskbar host is clean-room Win32 code; no TrafficMonitor GPL source is copied.
- Windows credentials use generation-chunk Credential Manager storage and fail closed; they are not written in plaintext. Native credential storage, path handling, process launch, and ConPTY have been exercised, but live provider authentication is not claimed.
- Windows tool logs are supported; WSL is not auto-discovered and requires a configured remote feed. Claude Cowork containers, Safari active-tab data, and Keychain import are unavailable. DeepSeek account access uses an external browser/manual token; CLI renewal supports Windows executables and standard npm Node shims. Compressed DeepSeek Harness logs require optional `zstd.exe`; otherwise JSON projection is used.
- Windows notifications are native message-box dialogs, not Windows toast notifications. Reminders run only while the app is open. Updates are manual downloads, not the macOS signed updater.
- Windows backups are raw SQLite `.db.sqlite` files; interchange SQLite directly. They are not macOS LZFSE-compressed backups.
- Startup registration is per-user. Resume and battery-saver callbacks are implemented, but suspend/resume behavior is not verified here.

## Keeping the port in sync

When merging upstream changes, keep the original macOS sources, tests, and CI authoritative for macOS. Update the shared-source/test allowlists in the Windows package manifest when files are added or moved; keep Windows-specific OS behavior behind its adapters. Run both platform workflows after a sync. Do not broadly extract the existing engine merely to make the Windows build convenient.
